# Conditional workflow selection

An agent may publish `workflow_selection_rule` after an independently retained,
exact-version workflow comparison. The rule connects observed method evidence to
actual future work. It is not an automatic global promotion or a causal claim.

## Production path

1. Publish and compare baseline and candidate `workflow_method` records using the
   existing original-observation, regression and independent-review contracts.
2. Propose input conditions, counterconditions, their evidence basis, limitations
   and a prospective test. The saved rule pins the comparison and both methods.
3. Recall the rule through `mode=capabilities` and read its exact original.
4. Use `workflow_instance` with `selection_rule` instead of `method`. The host
   evaluates typed scalar conditions against the declared inputs, then expands
   the selected method into the ordinary goal/live work graph.
5. Preserve the decision in each admitted task and durable method-use history.
   Inspect later failures and measured quality before proposing a new rule.

The schema is available through `evolution_rules`, topic `workflows`, on the
existing cloud and remote Desktop recall paths. Desktop remains an adapter; no
second selection engine or model call is added there.

## Selection and recovery

- All positive conditions must match, every exclusion must be known and false.
- Missing fields, wrong types and non-scalar results are unknown. They do not
  silently become false, zero or null. Unknowns select the preserved baseline.
- Matching exclusions and out-of-scope conditions also select the baseline.
- Inputs are declarations, not independently certified environmental facts.
  A coordinator must gather evidence and check the applicability of both methods.
- Both methods expose the same input and role names; internal steps/dependencies
  may differ. A different public interface still uses explicit planning.
- New work requires current evidence lineage. Existing claims retain the exact
  choice and replay only unfinished steps. A new rule or inputs need a new use.
- No role authorization, independent review, model routing, pause/stop, goal
  criterion or tool permission is changed. Ordinary plans do no additional I/O.

## Verification and interpretation

`CollaborationWorkflowSelectionTest` covers evidence-linked publication, typed
conditions, unknown data, exclusions, actual graph changes, discovery in later
turns, scoped access, tampering, goal/live admission, retained failure history,
stale evidence and partial replay. Existing workflow and method-history suites
cover shared execution behavior.

These are synthetic mechanism tests. Passing them does not demonstrate that a
model autonomously proposed a useful condition, that an input declaration is
true, that the condition has prospective validity, or that team intelligence
improved. No rule can convert model self-ratings into measured causal effects.
Real adoption, held-out quality, negative transfer and long-term retention still
need separate evidence. No paper, private protocol or raw experiment data belongs
in this repository.
