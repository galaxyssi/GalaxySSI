# Startup reply inbox isolation

## Baseline

On SM-T575, Android 1.1.39, real Codex recovery case
`live-final-1788974433882` passed exact-body, single-reply, Activity recreation,
and subsequent cold-start checks. Its first visible recovered reply still took
29,912 ms. Startup hydration spent 9,646 ms reading the global proactive insight
count before releasing transcript readiness and scheduling the inbox drain.
Global background initialization took 23,092 ms in an overlapping interval.
Those overlapping durations must not be added or used to explain all UI latency.

## Change

Android 1.1.40 (926) removes optional dashboard data from the initial transcript
hydration result. Once the conversation and runtime state are rendered, it
releases readiness, schedules the durable inbox, and requests the existing
asynchronous insight indicator refresh. The indicator still reads real encrypted
data; it is not replaced with a constant count or disabled.

Content-free startup diagnostics distinguish inbox executor queue time, bounded
page read time, runtime restoration, and response consumption. These are local
monotonic durations, not cross-device clock differences. Dispatch duration does
not prove that text is already visible; the live UI test remains authoritative.

No model, ASR/QNN, message encryption, protocol, pairing, or Desktop runtime
changes are included.

## Regression and live verification

`AgentHydrationIsolationDeviceTest` temporarily holds the global repository's
storage lock in the test process, opens an isolated conversation window, and
requires transcript readiness before releasing that lock. It deletes only its
own conversation and releases the lock in `finally`. This is a controlled
dependency regression, not a live Provider or overall startup latency benchmark.

The separate real recovery harness must use the production Codex path, drop only
its own final reply, restart the App, recover the archived exact body, render one
reply, recreate the Activity, and cold-start again. Do not loosen its visibility
deadlines, inject replacement replies, or resubmit an existing test task.

Full Run Kernel, device reboot, chaos, all Provider routes, and representative
performance percentiles remain separate acceptance requirements.

## Results on SM-T575

- Full build: 7m 30s; 3,407 unit tests in 494 suites, zero failures/errors,
  five existing skips.
- Repository, 73-library AArch64 16 KB, and QNN package audits passed.
- The new dependency test failed on installed 1.1.39 at the unchanged
  ten-second readiness assertion. On confirmed installed 1.1.40 it passed in
  3.035 seconds, with the dashboard lock still held at readiness.
- One earlier post-install test attempt started before the asynchronous
  installation was confirmed complete and reported `Process crashed`. It is
  retained as invalid test orchestration evidence, not counted as a pass or
  attributed to a production regression. The subsequent test started only after
  installation success and a package version check.
- Installation retained the original first-install timestamp and pairing/data.
- After making the reflected test lock explicitly non-null, the final test APK
  rebuilt successfully and the same regression passed again in 2.682 seconds
  (`build/startup-reply-isolation-final-device.log`). Production APK SHA-256:
  `B6DF20D99CB045047F11D58D7BD9F22EC150E202E8FF10B4C9BC22CDB50C428B`.

Real case `live-final-1788975917258` passed all four unchanged recovery phases.
Desktop had exactly one completed Codex execution. Its conversation was
`93c28e63-466c-4128-adde-43be798e2a96`; no reply or task was regenerated by the host.

| Measurement | Elapsed |
| --- | ---: |
| Subscription readiness | 2,403 ms |
| Readiness to exact recovered body | 34,112 ms |
| Connection start to recovered body | 36,515 ms |
| First visible recovered reply | 18,420 ms |
| UI including Activity recreation and deduplication | 19,169 ms |
| Subsequent cold-start visibility | 2,510 ms |

Hydration completed in 1,641 ms instead of the baseline's 11,246 ms. Inbox
queue/read time was 1/78 ms for two replies. The first dispatch still spent
1,893 ms restoring a runtime and 9,935 ms consuming the response; the second
spent 786/1,578 ms. Global background initialization overlapped those operations.
Further response-consumption attribution is required; this change does not claim
to remove that remaining delay.

The network recovery sample includes three eight-second query timeouts and
expired responses, followed by exact-body recovery. Desktop lookup/page creation
took milliseconds and its publish calls took 260-401 ms, which does not prove
delivery. The batch also contained other unavailable observations; that aggregate
outcome is not failure of the recovered test reply.

These are individual samples, not representative P95/P99 measurements or proof
of the five-second recovery objective. The slower network sample is retained.

Evidence: `build/startup-reply-isolation-{build,before,after,
after-confirmed-install,repo,16kb,qnn}.log`, the unit-summary JSON, and
`build/live-final-1788975917258/` (four phase logs, UI timings, recovery diagnostics,
monotonic stage timings, and one-execution check).
