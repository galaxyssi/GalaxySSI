# Android Full-Page Capture

## Entry And Execution

The floating menu places **Analyze the entire page** immediately after the existing current-screen action. This means the current target App window from top to bottom, not every screen in the App or automatic link navigation. The home window supplies the reasoning provider, model and effort through the existing screen-assistant routing bridge.

A dedicated single worker collects visible structure and target-window screenshots, writes each segment to private storage, rewinds using observed scroll nodes, and then advances the largest accessible scrolling region. Password/editable text is excluded from extracted content. Screens with password nodes retain redacted structure but no raw screenshot. On Android 14+ the window screenshot excludes the assistant; older supported versions use the existing two-frame overlay hiding path. A capture does not authorize a model to mutate the phone.

Each scroll/capture uses the shared physical-display operation lock. Pause waits outside that lock; Finish capture unpauses and returns the collected subset, while Cancel never submits it. Target-window/App/Chrome-address changes stop collection. Observed external clicks, edits and scrolls outside the expected collector-scroll interval interrupt collection rather than combining unrelated evidence. This heuristic is not a universal detector of every possible gesture or same-window SPA navigation.

The compact capture panel displays collected screens, pause/resume, finish, cancel and collapse. No percentage is shown when the end is unknown. The underlying App remains touchable outside the panel, but collection necessarily scrolls its visible content; this is not an invisible clone of the App. Users should pause before interacting. Original position restoration is best-effort and recorded in metadata; it is skipped after interruption/cancellation.

## Data And Completeness

Each capture has a UUID-private directory under `agent-rich-output-v2/screen-assistant/pages`. A manifest checkpoint and numbered JSON/JPEG files persist collected evidence. Cancellation/process loss does not resume scrolling unattended. Partial files can remain locally; unfinished captures are not presented as complete. Checkpoints currently preserve evidence, not a restartable automatic capture job.

Only adjacent viewport text overlap is removed. Repeated sentences elsewhere remain; screenshot changes retain image-only evidence. The HTML reading copy escapes all source text, embeds local screenshots and has no executable source markup. It is a reconstruction, not the source website HTML. A text companion preserves collected text; a PDF is exported on demand using the already bundled PDFBox library with disk-backed document streams, direct JPEG embedding and bounded bitmap fallback for text-only segments. HTML/PDF exports go to Downloads/GalaxySSI using pending MediaStore writes with failure cleanup.

The viewer disables scripts, file access, network loads and external navigation. Capture attachments are excluded from automatic knowledge import. They are still local artifacts and explicit input to the selected Agent; this is not a claim of zero exposure to the configured provider.

`complete=true` requires a verified top, a rejected forward scroll at the bottom, no truncated structure and no missing required screenshot. An unchanged/rejected/stalled action is not silently treated as successful navigation. No accessible scroll node means visible-screen-only coverage, not full-page coverage. Infinite feeds stop only through user intervention or safety boundaries and remain partial. The per-capture storage budget is the smaller of 128 MiB and 10% of available storage; less than 32 MiB remaining space stops collection. A 1,000-operation traversal safety boundary prevents unbounded inaccessible/infinite loops. These are local resource/safety limits, not model search-time budgets.

## Agent Handoff

Current-screen analysis captures the actual target-window image even when accessibility exposes Gallery buttons or other text. UI labels are supplementary evidence, deduplicated and bounded to 4,000 characters without node IDs, coordinates or action flags. Recognized password fields disable this image capture and exclude password/editable text from supplementary evidence. The original UI-action tools still use their existing full structured observations.

The public transcript and connector history store the question separately from the internal analysis instructions and evidence envelope. Screenshot attachments remain visible. Saved pending requests retain the public question rather than an internal evidence dump. Existing historical messages are not rewritten or deleted. Identification should lead with the subject and meaning, verify the exact model before using outside specifications, and distinguish promotional claims from verified capability. Concision alone is not treated as a quality check.

Independent analyses do not append old conversation summaries, personal/knowledge context blocks, older screen context or observed-control messages. Explicit follow-up questions retain the normal bounded conversation context. The host snapshots this distinction and the public question per turn; changing a shared follow-up request cannot alter the earlier turn's metadata. Both cloud and Desktop dispatches apply this rule, including forced attachment connectors and provider fallback. This does not globally disable Agent memory. A prior live screen-analysis request carried a real image but also 39,220 prompt characters containing unrelated topics and UI node paths, so absence of an image alone did not explain its quality problems.

Current-screen and full-page analysis are explicitly read-only, independent requests. Android does not restore an earlier supervised phone-operation goal or steer an unrelated active turn into these requests. The host binds `request_kind=screen_analysis` to the owning turn and persists it in connector action parameters, so a Codex-to-cloud fallback retains the same scope after a process-local binding is released. MQTT and the private Desktop request snapshot retain it. Desktop uses a fresh, read-only Codex run, accepts a text answer without requiring a file or installation receipt, and carries the same contract through the Worker adapter. Ordinary installation and artifact tasks retain their existing verification requirements. This is not a claim that an interrupted analysis is fully restored after phone process death.

Both cloud and Desktop response policies lead with the conclusion and normally use one short paragraph or up to three short points. Ordinary answers target about 150-250 Chinese characters or 80 English words without truncating the delivered text. Requested detailed analysis, necessary safety information, uncertainty and supporting citations take precedence over that style target. The default current-screen question asks only for key information rather than an exhaustive visual inventory and unsolicited recommendations.

The Android execution-loop routing also excludes independent screen-analysis requests from supervised phone-operation planning. Skipping only submission-time continuation is insufficient: the runtime could otherwise reinterpret a plain model answer as a structured phone ActionPlan because earlier project context remains in the conversation.

The regular supervised submission receives the saved HTML and text files, not hundreds of separate MQTT image attachments. The read-only native `galaxyssi.phone.page.read` tool is bound to the owning turn and returns saved text, page continuation and screenshot URI. It cannot read another turn's capture or arbitrary filesystem paths. Serialized observations stay below 3,500 characters, with offsets recomputed after sizing so no text is skipped.

The task requests all segments, useful conclusions and explicit missing coverage. It does not imply that a model has actually read every segment merely because capture succeeded. Autonomous chunk-by-chunk model completion, verified read coverage and very long multimodal model analysis need separate end-to-end acceptance. Remote Agents can use the attached complete files; the implementation does not assume a phone content URI is a Desktop filesystem path.

## Test Coverage

Pure policy cases cover scroll selection, offscreen/password/editor exclusion, adjacent overlap, repeated text, markup escaping and window/address identity. Controlled device cases cover middle-to-top traversal, all segments, position restoration, HTML/PDF output, early finish, cancellation, paused cancellation, target changes, stalled scrolling, turn isolation, escaped-text pagination and a real 80-row Android fixture. Device cases use generated capture directories and never send a real Agent request. Passing compilation is not a substitute for these device tests.

## Validation Status

The v1.3.10 / 1054 build passed `:app:assembleDebug`, `:app:assembleDebugAndroidTest` and 156 focused unit tests across 18 suites, with no failures or errors. The focused selection includes screen-assistant policies, phone controls, system-tool planning, home routing, model selection and local voice policies. Kotlin source-size checks and `git diff --check` also passed.

The v1.3.11 / 1055 image-evidence, context-isolation and transcript-separation build passed both APK targets and 155 focused unit tests across 15 suites, with no failures or errors, and was installed over the existing App on S26U without removing configuration or downloaded models. The unlocked rerun passed all 29 focused device cases after the preceding locked-screen attempt failed seven cases. The replacement shared mini-chat build subsequently passed 35 device cases, including the same nine full-page cases and actual 80-row fixture traversal. The collector tests verify HTML/PDF generation, not manual viewer rendering and Downloads export. Real long-page Agent reading and exhaustive semantic coverage remain separate acceptance work.

A live original-poster Codex run used 1,986 prompt characters and a 98,513-byte image, returned a concise 287-character answer correctly identifying Wigain Flow, and delivered the public question, image and rich reply to S26U. The model run took 39.456 seconds and the measured end-to-end trace took 59.053 seconds, including 16.589 seconds before Desktop receipt; this is not a performance acceptance claim. A separate DeepSeek run completed but still described Gallery controls and produced a verbose answer. Its later brevity refinements remain pending live acceptance.

Desktop regression ran 90 Python cases (89 passed, one skipped Windows process test) and 61 JavaScript cases with no failures. Coverage includes screen-request isolation, ordinary install verification, concise policy in fresh/existing Codex prompts, private snapshot recovery and the Worker adapter. A recovered screen request uses a fresh read-only Codex run and receives the screen-analysis execution contract even on the fast chat path. These mocked-provider tests do not substitute for a live MQTT screen-analysis acceptance run.
