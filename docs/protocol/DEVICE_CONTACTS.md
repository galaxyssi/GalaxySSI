# Device Contacts and Pair Relationships

SignalASI represents a paired phone or Desktop as a device contact. Device
contacts are separate from the Agent contacts exposed by a Desktop.

## Identity layers

- Installation identity: the long-lived Signal identity key fingerprint.
- Device ID: stable metadata generated by one SignalASI installation.
- Desktop ID: stable contact ID derived from the Desktop identity.
- Route ID: a random 128-bit identifier created for one pair relationship.
- Display name: user-facing metadata that may be renamed without changing trust.

Trust decisions must use the installation identity and the pair route. They must
never use a display name, host name, model, or profile name as an authority.

## Display names

The phone creates a readable name from its system device name and SignalASI
profile. If no distinct profile name exists, it adds a short identity suffix.
Examples:

- `S26 Ultra - Helen`
- `S26 Ultra - A84C`

The Desktop creates a readable name from its product family and host name.
Examples:

- `ThinkPad T14 Gen 3 - DESKTOP-T14`
- `Studio workstation`

The UI renders the separator as a centered dot. Users may rename either contact.
A user alias survives a route rotation for the same verified identity.

## Many-to-many relationship

One Desktop registry may contain many phone clients. One Android installation
may contain many Desktop server links. Each relationship owns a unique topic set:

```text
signalasichat/v1/{server_route_id}/{client_route_id}/up
signalasichat/v1/{server_route_id}/{client_route_id}/down
signalasichat/v1/{server_route_id}/{client_route_id}/control
```

Messages, tasks, turns, attachment transfers, acknowledgements, and revocations
remain scoped by the pair route and their conversation and task identifiers.

## Pairing flow

1. The Desktop opens Mobile Gateway and selects Pair device.
2. The Desktop creates an expiring QR offer with its identity, device metadata,
   random route information, and selected access grant.
3. Android scans and verifies the offer, displays the Desktop device name and
   fingerprint, then publishes its signed device claim.
4. The Desktop records that phone as a paired device and returns its own device
   metadata in the encrypted confirmation.
5. Android stores one Desktop device contact plus the child Agent contacts that
   Desktop exposes.

The Desktop device contact targets the Desktop super-agent coordinator. Child
Agent contacts continue to target Codex, Hermes, Claude Code, OpenClaw, local
models, or other configured runtimes independently.

## Rotation and removal

- Re-pairing the same identity on the same Desktop revokes only its previous
  route, keeps its user alias, and creates a new route.
- Pairing another identity creates another client and does not replace existing
  clients.
- Removing a Desktop device contact on Android revokes that Desktop relationship
  and removes only its child Agent contacts.
- Revoking a phone on Desktop invalidates only that client's route. Other paired
  phones remain active.

## UI ownership

- Desktop: Mobile Gateway owns Pair device, the QR offer, paired phone list,
  rename, access summary, and revoke controls.
- Android: Contacts owns Desktop device contacts and their child Agent contacts.
  Device details show model, platform, host name, fingerprint, and current trust.
